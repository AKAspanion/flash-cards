# Sharing Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: the project's workflow policy names the executor (`run.executor`): ga:implement-with-subagents by default, or ga:implement. Follow the policy and this plan's Checkpoints. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A person can share a set as a read-only link, and anyone who opens the link can preview the set and copy it into their own library.

**Architecture:** Sharing writes a public copy to a new `shared-sets` collection: title, colour and cards with progress removed, plus the owner's uid for the rules. The owner's set keeps that copy's id in `shareId`. Creating or deleting the copy and setting or clearing `shareId` happen in one batched write. While a set is shared, each save also updates the copy. A new `/s/:shareId` route has a `public` meta that the auth guard lets through whether the person is signed in or not. A signed-out "Add to my library" goes through the existing login redirect and finishes the copy on the way back.

**Tech Stack:** Vue 3, Vuetify 4, Pinia, Vue Router, vue-i18n, Firebase 13 (Auth + Firestore), Firestore security rules, TypeScript, Vitest (jsdom, plus `@firebase/rules-unit-testing` on the emulator), Playwright with the Auth + Firestore emulators, GitHub Actions CI (`.github/workflows/ci.yml`, `deploy.yml`).

**Spec:** `docs/specs/2026-11-02-usability-features.md` (section 11; rules 2.1, 2.2, 2.4, 2.7, 2.8, 2.9, 2.10; data model 3.2; contracts 13)

- Rule 2.10: "Every online-only action, when offline, shows the existing message "You're offline. Connect to the internet to save." unless this spec gives another one."

### Task 1: Security rules for shared sets

**Files:**
- Modify: `firestore.rules`
- Test: `tests/unit/firestore.rules.spec.ts`

**Interfaces:**
- Consumes: existing rule helpers `signedIn()`, `ownsStored()`, `ownsIncoming()`, `validSet()` in `firestore.rules`.
- Produces (Tasks 3 and 4 rely on these rules in the emulator):

```
match /shared-sets/{shareId}
  get:    anyone, signed in or not
  list:   nobody
  create: signed in; ownerUid == request.auth.uid; keys exactly
          ownerUid, title, color, cards, updatedAt; title string, size <= 200;
          color string; cards string, size <= 900000; updatedAt == request.time
  update: stored ownerUid == request.auth.uid; incoming ownerUid unchanged; same shape as create
  delete: stored ownerUid == request.auth.uid

validSet(): additionally, shareId is absent or a string
```

**Spec:**
- §11.2: "The link is `/s/{shareId}`, where `shareId` is a random Firestore document id."
- §11.3: "The public copy holds only `ownerUid`, `title`, `color`, `cards` (with `learned` false and no `srs`) and `updatedAt`. No name, email, photo or labels."
- §11.8: "Rules: anyone may `get` a `shared-sets` document; nobody may `list` them. Only a signed-in user may create one, with `ownerUid` equal to their uid, only the five fields of 11.3, `title` a string of at most 200 characters, and `cards` a string of at most 900,000 characters. Only the owner may update (keeping `ownerUid`) or delete."

**Tags:** `security`

**Acceptance:**

Every other card field (`srs` and any unknown field) is dropped. `sharedSetFromDoc` treats the document as untrusted input: it parses `cards` with the same tolerant parser as sets, makes `title` `''` when it isn't a string, and makes `color` `#E91E63` when it isn't `#` plus 6 hex digits.
