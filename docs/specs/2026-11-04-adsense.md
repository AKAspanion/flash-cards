# AdSense Spec

**Date:** 2026-11-04
**Status:** Draft, for the developer's review
**Scope:** Show one Google AdSense banner unit in two fixed places in the web app (and so in the Android TWA), with
the Content-Security-Policy, `ads.txt`, consent and privacy policy that it needs.

## 1. Why, and what's agreed

The developer wants the app to earn from ads, and has an approved AdSense account. Decided by the developer on
2026-11-04 (recorded in `knowledge/decisions/`):

| Decision | Rule |
|---|---|
| `adsense-banner-ads` | One manual, responsive AdSense display unit, at the bottom of Home and of Info. No Auto ads. Loaded only when its env vars are set. |
| `adsense-consent-by-google` | Consent for the EEA, the UK and Switzerland is AdSense's own "Privacy & messaging" GDPR message, set up in the AdSense dashboard; the app has no consent code of its own. |

What this changes, and what it leaves alone:

- The published privacy policy promises "We don't show ads" (`privacy.use.body`, from
  [the Android TWA spec](2026-11-04-android-twa.md) §privacy). That promise is withdrawn here, in the same release that
  turns ads on (§5).
- [decisions/no-analytics-yet](../../knowledge/decisions/no-analytics-yet.md) still holds: Firebase Analytics stays
  off. AdSense's own measurement is Google's, under the consent above, and is not analytics the app reads.
- [decisions/audience-13-and-over](../../knowledge/decisions/audience-13-and-over.md) still holds; it keeps the app out
  of Play's Families policy, so AdSense needs no child-directed tagging.
- The TWA runs in Chrome, not a WebView, so AdSense's web ads are allowed in it; the Android project doesn't change.

## 2. Global rules

- 2.1 Every new or changed user-facing string is in both `src/locales/en.json` and `src/locales/hi.json`. The English
  is the copy in this spec, word for word. The implementer writes the Hindi; the PR lists it for a Hindi reader.
- 2.2 With either AdSense env var empty, the app behaves exactly as today: no script, no element, no request to a
  Google ad domain. Dev, the emulators, CI and e2e run this way.
- 2.3 An ad never blocks, shifts or breaks the app: a failed or blocked script, being offline, or an unfilled slot
  leaves nothing on screen and no error for the user.
- 2.4 No new npm dependency.

## 3. Configuration

- 3.1 Two env vars, read like the others through `import.meta.env` (prefix `VUE_APP_`):
  - `VUE_APP_ADSENSE_CLIENT` — the publisher ID, `ca-pub-` followed by digits.
  - `VUE_APP_ADSENSE_SLOT` — the display unit's `data-ad-slot`, digits.
- 3.2 Both are added, empty, to `.env.example` with a comment ("Optional: Google AdSense banner; no ads when empty"),
  and to the `env:` block of `.github/workflows/deploy.yml` as `${{ vars.VUE_APP_ADSENSE_CLIENT }}` and
  `${{ vars.VUE_APP_ADSENSE_SLOT }}`. They are public values, like the Firebase web config, and are not added to the
  deploy job's required-vars check: an unset pair just means no ads.
- 3.3 A value that doesn't match its pattern (`^ca-pub-\d+$`, `^\d+$`) counts as empty (2.2), so a typo can't inject
  markup or load a script from a crafted URL.

## 4. The banner

### 4.1 `src/services/ads.ts`

- `adsConfig(): { client: string; slot: string } | null` — both vars valid (3.3), else `null`.
- `loadAdSense(client)` — appends, once per page load, `<script async crossorigin="anonymous"
  src="https://pagead2.googlesyndication.com/pagead/js/adsbygoogle.js?client=<client>">` to `document.head`. A
  second call is a no-op. A script `error` event is swallowed (2.3).
- `requestAd()` — `(window.adsbygoogle = window.adsbygoogle || []).push({})`, inside `try`/`catch` that swallows the
  error (2.3).

### 4.2 `src/components/AdBanner.vue`

- Renders nothing when `adsConfig()` is `null`.
- Otherwise renders, inside a wrapper with the page's side margin and a small top margin:
  `<ins class="adsbygoogle" style="display:block" data-ad-client=<client> data-ad-slot=<slot>
  data-ad-format="auto" data-full-width-responsive="true">`, then on mount calls `loadAdSense(client)` and
  `requestAd()` once.
- Each mount is a fresh `<ins>` and one push, so leaving and coming back to a screen asks for a new ad.
- An unfilled slot is hidden: `ins.adsbygoogle[data-ad-status="unfilled"] { display: none }`, so no blank box stays.
- No label, close button or placeholder of its own; AdSense draws its own "Ad" marking.

### 4.3 Where it goes

- 4.3.1 **Home** (`src/views/Home.vue`): below the sets list, as the last thing on the page, once sets have finished
  loading (not under the loading shimmer). Shown whether the list has sets or shows the empty state. Never between
  sets.
- 4.3.2 **Info** (`src/views/Info.vue`): after the last card on the page.
- 4.3.3 Nowhere else. In particular never on study (`/:id/view`), add/edit, login, profile, settings, bin,
  `/privacy` or `/delete-account`.
- 4.3.4 Once loaded, Google's script stays in the page for the rest of the visit. Only the Home and Info banners ask
  it for ads, and Auto ads stays off in the dashboard (§8), so no other screen shows one.

## 5. Privacy policy

`src/views/Privacy.vue` and both locales:

- 5.1 `privacy.use.body` becomes: "To sign you in and to show and save your sets. We don't use analytics, and we
  don't sell your data."
- 5.2 A new section after "How it is used", `privacy.ads`, in the same icon-row style as the others (icon
  `mdi-bullhorn-outline`):
  - title: "Ads"
  - body: "FlashCards shows ads from Google AdSense at the bottom of some screens, never while you study. Google and
    its partners use cookies and device identifiers to show and measure these ads, and may personalise them. If you
    are in the EEA, the UK or Switzerland, you are asked for your consent first. You can turn off personalised ads at
    adssettings.google.com, and read how Google uses this data at policies.google.com/technologies/partner-sites."
  - The two addresses are links (`https://adssettings.google.com` and
    `https://policies.google.com/technologies/partner-sites`), opening in a new tab with `rel="noopener noreferrer"`.
- 5.3 `privacy.updated` becomes "Last updated: " and the date the change is built, in the same format.

## 6. Hosting

### 6.1 `public/ads.txt`

One line, `google.com, pub-<digits>, DIRECT, f08c47fec0942fa0`, where the digits are the publisher ID's (3.1). The
developer supplies the ID; the plan's task waits for it rather than guessing. Served at `/ads.txt` (Vite copies
`public/`; Firebase serves it as a file before the SPA rewrite).

### 6.2 Content-Security-Policy (`firebase.json`)

Added to the existing policy; nothing removed, no other header changed:

| Directive | Added |
|---|---|
| `script-src` | `https://pagead2.googlesyndication.com https://*.googlesyndication.com https://adservice.google.com https://*.adtrafficquality.google https://fundingchoicesmessages.google.com` |
| `frame-src` | `https://googleads.g.doubleclick.net https://tpc.googlesyndication.com https://*.googlesyndication.com https://www.google.com https://*.adtrafficquality.google https://fundingchoicesmessages.google.com` |
| `connect-src` | `https://pagead2.googlesyndication.com https://*.googlesyndication.com https://*.adtrafficquality.google https://fundingchoicesmessages.google.com https://*.doubleclick.net` |

`img-src` already allows `https:`, and `style-src` already allows `'unsafe-inline'`, which the consent message needs.
Google doesn't publish a fixed list; after the first deploy the developer opens Home in Chrome and adds any CSP
violation the console reports for a Google ad domain (§8).

### 6.3 Service worker

No change. The Workbox config in `vite.config.ts` precaches only the app's own files and has no `runtimeCaching`, so
ads are never cached or served offline.

## 7. Security

Google's ad script runs in the app's own origin, with the same access to the page as the app's code, on every screen
after Home or Info first loads it (4.3.4). This is accepted as the cost of AdSense; it is limited by:

- the CSP allowing only Google's ad domains (6.2), and `frame-ancestors 'none'` staying;
- the script URL built only from a validated publisher ID (3.3);
- nothing else on the site being changed to suit it (no `unsafe-eval`, no wider `default-src`).

No route, store, Firestore rule or user input changes, so nothing here meets hostile input from users.

## 8. Done by the developer, outside the code

1. Set the GitHub repository variables `VUE_APP_ADSENSE_CLIENT` and `VUE_APP_ADSENSE_SLOT`.
2. In AdSense: add the site, turn **Auto ads off** for it, and publish the "Privacy & messaging" GDPR message for the
   EEA, UK and Switzerland.
3. After the deploy: check `/ads.txt`, open Home in Chrome and look for CSP violations (6.2).
4. In the Play Console: answer **Contains ads: Yes**, and update the Data safety form (device or other IDs, collected
   by Google for advertising).

## 9. Tests

Written first, each watched failing:

- `tests/unit/ads.spec.ts` — `adsConfig` is `null` when either var is empty or malformed, and returns both when valid;
  `loadAdSense` adds one script with the client in its URL however often it's called; `requestAd` doesn't throw when
  `push` throws.
- `tests/unit/AdBanner.spec.ts` — renders no `<ins>` and loads no script with the vars empty; renders the `<ins>` with
  the client and slot, and pushes once, with them set.
- `tests/unit/csp.spec.ts` — the CSP in `firebase.json` contains each domain in 6.2 under its directive, and still has
  `frame-ancestors 'none'` and no `unsafe-eval`.
- `tests/unit/adsTxt.spec.ts` — `public/ads.txt` has one line, in the 6.1 format.
- The e2e suite runs unchanged, with the vars empty (2.2); the existing public-pages e2e covers the privacy page still
  rendering.

## 10. Out of scope

- More ad units or placements, interstitials, rewarded ads, Auto ads.
- An in-app consent tool or a "remove ads" purchase.
- AdMob or any native Android ad SDK.
